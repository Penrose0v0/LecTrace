# Chirp 3 流式：endpointing_sensitivity STANDARD vs SHORT（2026-10-17）

## 材料与方法

- 音频：线上真实课堂录音（GCS `lectrace-recordings`）里切的 8 段 × 120 秒，来自 4 节不同的课
  （2 段学生发表 / 讨论，含多人轮流说话和十几秒安静；其余为老师讲课），共 16 分钟。16 kHz 单声道 PCM。
- 送法：按实时速率一帧 2730 字节（≈85 ms）喂给 v2 `StreamingRecognize`（us 区域，`chirp_3`，`interim_results=True`），
  与前端上行方式一致。每段每个模式各跑一次，4 路并发。基线：线上现用的 v1 `default`（Tokyo）。
- 延迟定义：`到达时刻 − result_end_offset`（v1 用 `result_end_time`），即这段话说完到它出现在屏幕上的间隔。
  「字幕延迟」统计所有屏幕更新（interim + final），「final 延迟」只统计定稿。
- CER：定稿拼接后与参照做字符编辑距离 / 参照长度，先去标点空白；「再去填充词」版本额外去掉 え/ま/あの/えっと 等。
  **参照不是人工标注**，是 OpenAI `gpt-4o-transcribe` 的离线转写（它会删掉填充词、偶有改写），
  所以数字是「与另一套系统的分歧率」，看模式之间的相对差，不是绝对准确率。v1 列给出这个分歧率的底线。

## 结论

- **SHORT 换来的是约 0.5 秒**：字幕 P50 2.1→1.6、P90 5.3→3.9，final 最大等待 17→14.6 秒，切分从每分钟 3.8 次到 4.4 次。
- **代价是准确率**：去填充词 CER 37%→56%，字数覆盖率 0.96→0.90（有三段丢了 20–40% 内容），还出现一次幻觉循环。
  STANDARD 的分歧率和 v1 持平（37% 对 37%），说明这批音频对任何系统都难，STANDARD 没有比 v1 更差；SHORT 明显更差。
- **Chirp 3 的 interim 基本不能当实时字幕用**：16 分钟只有 56 条（v1 有 3487 条），第一条平均要等 30–40 秒才出现。
  它是「一句说完整体定稿」的模式，定稿平均比 v1 晚 1 秒、最坏晚十几秒。对 Catch-up（只用定稿）没影响，对「正在识别」灰字预览影响很大。
- **建议保持 STANDARD（当前默认）**。要更快的屏幕反馈，不是调 SHORT，而是切回 v1 或者做 v1 预览 + Chirp 3 定稿的混合。
